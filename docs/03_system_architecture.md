# 系统架构与设计决策

> 基于 Dify Chatflow 的电商智能客服系统架构说明

## 一、整体架构：三层漏斗

### 为什么是"三层漏斗"而不是端到端？

AI 客服系统最常见的做法是"一个大模型全搞定"——用户说什么，大模型直接回答。但这种方式有三个问题：

1. **不可解释** — 回答错了不知道是哪一步错的
2. **不可调试** — 想优化某个场景不知道从哪下手
3. **不可控** — 关键业务场景（如退款、投诉）不能完全交给模型

三层漏斗架构把过程拆解开，每一层的输入输出都可以单独观测和优化。

```
                    ┌─────────────────────┐
                    │     用户输入         │
                    └──────────┬──────────┘
                               ↓
        ┌──────────────────────────────────────┐
        │  第 1 层：意图分类 LLM               │
        │  （温度 0.3，保证分类稳定性）        │
        │  分类：知识类 / 办理类 / 混合类 / 闲聊 │
        └───────┬──────────┬─────────┬─────────┘
                ↓          ↓         ↓
          知识类        办理类     混合类/闲聊
                ↓          ↓         ↓
        ┌───────┴──────────┴─────────┴─────────┐
        │  第 2 层：分支路由                    │
        │  8 个 IF/ELSE 条件分支               │
        │  商品咨询 / 订单查询 / 退款换货 / 投诉 │
        └───────┬──────────┬─────────┬─────────┘
                ↓          ↓         ↓
          知识检索     API 调用   状态机引导
                ↓          ↓         ↓
        ┌───────┴──────────┴─────────┴─────────┐
        │  第 3 层：生成 / 执行                 │
        │  LLM 生成回复 / 执行业务逻辑         │
        └──────────────────────────────────────┘
```

## 二、各层详细设计

### 第 1 层：意图分类

**工具：** Dify LLM 节点 + 问题分类器

**分类体系：**

| 大类 | 子类 | 判定依据 |
|------|------|---------|
| 知识类 | 商品咨询、政策咨询 | 疑问语气、名词性问题 |
| 办理类 | 退款、退货、换货、改单、取消、投诉、订单查询 | 祈使语气、动作动词 |
| 混合类 | 既有咨询又有办理 | 核心诉求判定法 |
| 闲聊/其他 | 闲聊、无关、转人工 | 低置信度 |

**温度设置：0.3**
- 意图分类需要稳定性，不能每次分的都不一样
- 温度低 = 输出更确定

### 第 2 层：分支路由

**8 个 IF/ELSE 分支：**

| 分支 | 触发条件 | 处理方式 |
|------|----------|---------|
| 商品咨询 | 知识类 + 商品/政策相关 | 知识检索 → LLM 润色生成 |
| 订单查询 | 办理类 + 查询订单/物流 | 参数提取 → HTTP API → 结果格式化 |
| 退款换货 | 办理类 + 售后动作 | 状态机引导 + 业务逻辑处理 |
| 投诉 | 办理类 + 追责/赔偿/曝光 | 投诉分级 → 自动处理/升级人工 |
| 其他 | 低置信度 / 闲聊 / 转人工 | 兜底回复 / 转人工引导 |
| 边界混淆 | 介于两个分支之间 | 二次确认 / 规则排除 |

**关键设计：大类路由 + 子场景细分**

退款、退货、换货、改单、取消——这些本质上都是"售后办理"，属于同一大类。

- **大类层面**：只判断是不是售后办理（一个分支入口）
- **子场景层面**：用 `action_type` 字段细分（refund / exchange / cancel / modify）

为什么这么设计？
- 分支拆太碎 → 维护成本高、路由错误率上升
- 大类统一 → 共享状态机和业务逻辑，子场景只差异化处理

### 第 3 层：生成 / 执行

**知识类 → 知识检索 + LLM 生成**
- 检索配置：Top K = 6, score_threshold = 0.5, 关键词权重 = 0.5
- 生成约束：基于检索结果回答，禁止编造，200 字以内
- 兜底机制：检索未命中 → 明确拒答 + 转人工引导

**办理类 → 状态机 + 业务逻辑**
- 每个分支有独立状态机
- 状态机变量跟踪对话进度（如 other_step、refund_step）
- 保证多轮对话不会跳步、不会乱序

## 三、状态机设计

### 为什么用状态机？

客服场景的多轮对话（如退款流程、投诉流程）有明确的步骤流转。纯 LLM 驱动的多轮对话容易跳步、乱序、忘记上下文。状态机保证了：

- **确定性** — 该走哪一步就走哪一步
- **可追踪** — 当前在哪个状态一目了然
- **可恢复** — 对话中断了可以从当前状态继续

### 退款换货状态机（示例）

```
initial → confirm（确认意向）→ get_order（索要订单号）→ check_order（查询订单）
                                                                  ↓
                                          可退 → ask_reason（询问原因）→ process（处理退款）
                                                                  ↓
                                          不可退 → explain（解释原因）→ 结束
```

## 四、RAG 检索配置

| 参数 | 值 | 说明 |
|------|-----|------|
| Top K | 6 | 返回 6 个最相关的片段 |
| score_threshold | 0.5 | 低于 0.5 分的片段过滤掉 |
| 关键词权重 | 0.5 | 关键词匹配的权重占比 |
| 召回模式 | 混合检索 | 向量检索 + 关键词检索 |

### 为什么 score_threshold 设 0.5？

这是一个平衡点：
- 太低 → 引入无关内容 → 幻觉风险上升
- 太高 → 漏召回 → 答非所问、转人工率上升

0.5 是通过对比实验调出来的最优值。

## 五、关键设计决策

### 决策 1：为什么选 Dify 而不是自研？

- **产品阶段**：MVP 验证阶段，速度比完美重要
- **定位匹配**：Dify 的可视化工作流正好匹配"可定制"定位
- **开源可控**：数据自主可控，符合定位
- **生态丰富**：内置 RAG、LLM、HTTP、代码执行等节点

### 决策 2：为什么退款/退货/换货合并为一个大类？

- 业务本质相同 — 都是售后办理
- 共享状态机和业务逻辑 — 减少重复
- 子场景用 action_type 区分 — 既统一又灵活
- 避免分支爆炸 — 拆成 N 个分支维护成本指数上升

### 决策 3：为什么用状态机而不是纯 LLM 多轮？

- 客服场景的流程是确定性的 — 不需要模型"创造性"地走流程
- 状态机更稳定、可控、可调试
- LLM 负责"理解"和"生成"，状态机负责"流程控制" — 各司其职

### 决策 4：为什么要做防幻觉兜底？

- 客服场景答错比不答更可怕 — 错误信息可能导致经济损失和投诉
- 检索未命中时，明确说"这个问题我暂时无法回答，已为您转接人工"
- 用户体验上：诚实 > 硬编
- 业务上：人工兜底是必要的安全网
