# V1 → V2 迭代记录

> 10 项核心优化 · P2 路由硬错误 + P3 信息完整性

## 一、迭代背景

V1 版本搭建完成后，通过评测体系发现了一批问题。按问题性质和优先级，分为两个批次：

- **P2**：路由硬错误 — 方向性错误，必须先修
- **P3**：信息完整性不足 — 质量优化，可以后做

> 优先级原则：先修正确性，再提完整性。路由错了，后面的生成再好也没用。

## 二、P2 路由硬错误修复（7 项）

### P2-1：分类器咨询 vs 办理区分

**根因：** 疑问语气的政策咨询被误判为办理动作。

**典型案例：**
- 用户："退款多久到账？"
- 错误路由：退款换货分支
- 正确路由：商品咨询分支（咨询政策）

**修复：**
- 分类器 prompt 增加名词/疑问形式关键词列表
- 显式列出"什么时候发货 / 几天能到 / 退款时效"等咨询示例
- 强化"疑问语气 = 咨询类"的判定权重

---

### P2-2：换货场景细化

**根因：** "换颜色 / 换尺寸 / 尺寸不对 / 发错了要换"等具体换货表述未命中强信号词。

**修复：**
- 换货类强信号词扩充：换颜色 / 换尺寸 / 发错了 / 颜色不对 / 尺码不对 等
- LLM 引导节点 prompt 区分退款与换货话术
- intent = exchange 时，禁止使用"退款 / 退货"等词汇

---

### P2-3：投诉类排除规则完善

**根因：** "我要找人工 / 转人工客服"被投诉分支的"转人工"强信号词捕获，误走投诉分支并幻觉补偿方案。

**典型案例：**
- 用户："我要找人工客服"
- 错误路由：投诉分支 → 生成补偿方案（幻觉）
- 正确路由：其他分支 → 转人工引导

**修复：**
- 投诉类新增排除规则：若用户仅说转人工 / 找人工 / 人工客服，且无任何投诉 / 追责 / 赔偿表述 → 归为其他
- 其他类强信号词扩充：找人工 / 转人工 / 人工客服 / 接人工
- 分类器示例中删除"转人工客服 → 投诉"的错误示例

---

### P2-4：混合意图核心诉求判定法 ⭐

**根因：** 固定优先级（投诉 > 退款换货 > 订单查询 > 商品咨询 > 其他）导致混合意图场景误判。

**典型案例：**
- 用户："我要退钱还要曝光你们"
- 旧逻辑：投诉优先级最高 → 走投诉分支
- 问题：用户的核心诉求是退款，曝光只是情绪威胁手段

**修复：核心诉求判定法**

从"固定优先级"改为"核心动作判定"：

| 判定原则 | 说明 |
|----------|------|
| 核心是办理售后 | 归为退款换货（即使附带抱怨/曝光） |
| 核心是追责/赔偿/曝光 | 归为投诉 |
| 查询是前置动作 | 归为订单查询（即使后面有抱怨） |
| 投诉动作词是情绪化伴随 | 不改变核心诉求分类 |

**混合意图判定规则：**

```
如果用户同时表达了多个意图：
1. 找出所有动作词（退款/退货/换货/投诉/曝光/查询/修改等）
2. 判断哪个是核心动作（用户最想达成的事）
3. 其他动作是情绪表达、伴随状态还是前置动作
4. 按核心动作分类
```

> 这不是简单地调几个关键词，而是从根本上改变了意图判定的范式。

---

### P2-5：改单/取消纳入售后大类

**根因：** 修改订单 / 取消订单 / 改地址等售后办理诉求路由不明确，部分被误判为其他分支。

**修复：**
- 退款换货类强信号词新增"取消 / 修改 / 改"作为办理动作
- LLM 意图识别新增 `action_type` 字段，枚举值：
  - `refund`：退款 / 退货
  - `cancel`：取消订单
  - `modify`：修改订单 / 改地址
  - `null`：未识别
- 退款换货分支新增「条件分支 9」和「LLM 取消/修改处理」节点

---

### P2-6：其他类扩充（非电商场景）

**根因：** 非电商场景的问题（医疗、机票、餐饮等）被各分支的弱信号捕获，回复不准确。

**修复：**
- 其他类新增"非电商场景"识别
- 典型场景：订机票 / 吃什么药 / 买电影票 / 今天股票怎么样
- 统一走兜底分支，回复"抱歉，我是电商客服助手，只能回答电商相关问题"

---

### P2-7：新增取消/修改处理节点

**根因：** 退款换货分支只有退款退货的处理逻辑，缺少取消/修改订单的专门处理。

**修复：**
- 新增节点：条件分支 9（if-else）— 根据 action_type 判断类型
- 新增节点：LLM 取消/修改处理 — 处理取消订单和修改订单诉求
- 新增连线：分类器投诉分支 → 参数提取器 → 变量赋值 → LLM 确认 → 条件分支

## 三、P3 信息完整性优化（3 项）

### P3-1：LLM 润色节点优化

**根因：** 150 字限制导致信息点被省略。

**典型案例：**
- 用户问 AirPods Pro 2 的参数
- 知识库有芯片 / 续航 / 降噪 / 防水 / 特殊功能
- 回复只说了芯片和续航，省略了降噪等维度

**修复：**
- 字数限制从 150 字放宽到 200 字
- 新增完整性约束："如果用户询问商品参数，必须覆盖检索结果中的所有参数维度（芯片、续航、降噪、防水、特殊功能等），不要遗漏任何维度"
- 约束优先级：信息完整性 > 简洁性

---

### P3-2：商品咨询类关键词扩充

**根因：** 退款多久到账 / 换货流程 / 质保期等政策咨询类查询未命中商品咨询分支，走了兜底。

**修复：**
- 商品咨询强信号词新增「退款/换货政策」类别
- 覆盖场景：退款多久到账、退款时效、换货多久能收到、换货流程、退货政策、质保期多久 等

---

### P3-3：投诉类新增物流/服务不满场景

**根因：** 物流慢、包装差、服务态度等轻度投诉场景分类不明确。

**修复：**
- 投诉类强信号词扩充：物流太慢了、包装有划痕、配送时间不合适、物流信息不更新、商品外盒有压痕、快递员态度差
- 新增排除规则：若用户核心诉求是退款/退货/换货（即使附带抱怨物流/包装），仍归为退款换货；若核心是追责/抱怨本身（非办理售后），则归投诉

## 五、效果预览

P2 + P3 优化后，预计：
- 路由错误率显著下降（尤其是混合意图和边界场景）
- 信息完整性得分提升
- 整体通过率预计 +2-3pp
