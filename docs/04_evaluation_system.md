# 评测体系设计

> 505 用例 · 7 维度 · 双通道判分 · 复评方法论

## 一、为什么需要评测体系？

很多 AI 产品的问题是：**你说它好用，凭什么？**

- "我觉得挺好的" — 主观感受，不可信
- "用户说好用" — 样本太少，有偏差
- "接了大模型肯定好用" — 想当然，没有数据支撑

**评测体系的目标：用数据说话，科学衡量 AI 产品的质量。**

## 二、评测集设计

### 2.1 用例规模

- **总量：505 条**
- 覆盖全部 8 个业务分支
- 5 种测试类型
- 3 个难度等级
- 每条用例 17 个字段

### 2.2 用例字段设计

| 字段 | 类型 | 说明 |
|------|------|------|
| case_id | string | 唯一标识，跨版本追踪 |
| category | enum | 所属大类（商品咨询/订单查询/退款换货/投诉/其他） |
| sub_category | enum | 子场景分类 |
| test_type | enum | 测试类型（单轮/边界/禁止表述/多轮/对抗） |
| difficulty | enum | 难度等级（简单/中等/困难） |
| user_input | string | 用户输入内容 |
| conversation_history | array | 多轮对话历史（多轮用例专用） |
| expected_branch | string | 期望分支 |
| expected_intent | string | 期望意图 |
| expected_answer_contains | array | 期望回答包含的要点 |
| must_not | array | 禁止出现的表述 |
| expected_human_handoff | bool | 是否期望转人工 |
| reference_knowledge | string | 关联知识库条目 |
| priority | enum | P0/P1/P2 优先级 |
| tags | array | 标签 |
| notes | string | 备注 |

### 2.3 测试类型覆盖

| 测试类型 | 占比 | 目的 | 典型用例 |
|----------|------|------|---------|
| 单轮功能 | ~50% | 基础场景覆盖 | "发货时效是多久？" |
| 边界值测试 | ~15% | 临界/模糊场景 | "物流太慢了" |
| 禁止表述 | ~10% | 合规红线检测 | "加我微信私聊" |
| 多轮对话 | ~15% | 上下文连贯性 | 退款流程多轮引导 |
| 对抗测试 | ~10% | 恶意诱导/混合意图 | "退钱还要曝光你们" |

## 三、评分维度（7 维）

| 维度 | 分值 | 说明 |
|------|------|------|
| 信息完整性 | 1-5 | 回答是否覆盖了所有关键信息点 |
| 忠实度 | 1-5 | 回答是否基于知识库，有无幻觉 |
| 分支路由正确性 | 1-5 | 是否走了正确的业务分支 |
| 答案相关性 | 1-5 | 回答是否和用户问题相关 |
| 意图识别准确性 | 1-5 | 意图理解是否准确 |
| 语气合规性 | 1-5 | 语气是否专业、友好、合规 |
| 边界正确性 | 1-5 | 边界场景处理是否正确 |

### 通过判据

- **总分通过**：7 个维度加权平均 ≥ 4.0 分
- **硬指标通过**：无违规（must_not_violation = false）+ 无幻觉（faithfulness ≥ 4）
- **最终通过**：总分通过 AND 硬指标通过

## 四、双通道判分机制

### 4.1 为什么是双通道？

| 方案 | 优点 | 缺点 |
|------|------|------|
| 纯代码判定 | 100% 稳定、可复现 | 只能处理精确匹配，无法处理语义 |
| 纯 LLM 判定 | 能处理语义判断 | 不稳定、有偏差、成本高 |
| **双通道（代码 + LLM）** | 兼顾稳定与准确 | 设计复杂度稍高 |

### 4.2 通道 1：确定性预检（代码级）

处理能**确定**的事情，用代码精确匹配，结果 100% 可复现。

**① must_not 精确匹配**
- 逐字检查禁止表述列表
- 命中即判定违规，标记 must_not_violation = true
- 零容忍，不做语义模糊判断

**② expected_points 宽松匹配**
- 检查期望要点是否都被覆盖
- 支持多种宽松匹配策略：
  - 精确子串匹配
  - **范围语义匹配**：期望"1-7 天"，回复"1-3 天 + 3-7 个工作日"→ 整体覆盖即命中
  - 数字单位宽松匹配："7 天"和"7个工作日"视为相关
  - 前缀匹配："退款"和"退款时效"视为相关

### 4.3 通道 2：LLM 裁判（语义级）

处理需要**语义理解**的事情，用大模型打分。

**7 个维度逐一评分，每个维度 1-5 分。**

裁判 Prompt 核心原则：
- 给出明确的评分标准和示例
- 要求输出评分理由（comment）
- 结构化输出（JSON）

## 五、裁判系统迭代

### v4.0：基线版 — 话题内容判定法

**问题：** 按回复的话题内容判分支。
- 看到"退款"两个字 → 判退款换货分支
- 看到"改地址" → 判路由错误

**结果：** 大量假失败。
- "退款多久到账" 明明是政策咨询（商品咨询分支），被判成退款办理
- 裁判系统性偏差，评测结论不可信

### v4.3：核心突破 — 行为特征判定法

**核心洞察：话题内容 ≠ 分支路由。**

同一个话题（退款），行为不同，分支就不同：
- "退款多久到账？" → 提供信息 → 商品咨询分支
- "我要退款。" → 引导办理 → 退款换货分支

**各分支行为特征：**

| 分支 | 行为模式 | 典型表现 |
|------|----------|---------|
| 商品咨询 | 直接解答 | 给答案、引用知识库、不索要订单号 |
| 退款换货 | 引导办理 | 确认意向、要订单号、问原因、引导寄回 |
| 订单查询 | 查询数据 | 提供订单/物流信息、需要订单号 |
| 投诉 | 处理追责 | 道歉、记录、升级、赔偿方案、安抚 |
| 其他 | 兜底/转人工 | 无法回答、转接人工、身份说明 |

**v4.3 五项关键改进：**
1. 行为特征判定法（核心）
2. 大类与子场景区分原则
3. 操作流程咨询特殊判定
4. 范围语义匹配
5. 确定性预检覆盖机制

### v4.4：精修版

在 v4.3 基础上进一步精修判定规则，处理边界场景。

## 六、复评方法论

### 6.1 为什么需要复评？

**问题场景：** 我们做了 V2 → V3 的优化，想看看提升了多少。

**直接对比的陷阱：**
- V2 用旧裁判（v4.0）测的
- V3 用新裁判（v4.4）测的
- 而且中间还修正了一些用例的期望

→ 两个版本的差异里，混着"评测工具的变化"，不只是"系统行为的变化"

→ 对比不公平，结论不可信

### 6.2 什么是复评口径？

> 用**同一套** v4.4 裁判 + 修正后的用例定义，对 V2 的**原始回复**重新打分。

这样 V2 和 V3 的差异，就只反映系统行为的真实变化了。

### 6.3 复评的反直觉发现

| 指标 | V2 旧口径 | V2 复评后 | 差异 |
|------|----------|----------|------|
| 幻觉率 | 3.0% | 8.3% | +5.3pp |
| 通过率 | 96.8% | 94.3% | -2.5pp |

**旧裁判系统性低估了风险。**

旧裁判 v4.0 太"宽容"了——很多幻觉它没认出来。复评之后才发现，V2 的实际质量比我们以为的要差。

> 这个发现很重要：**评测工具本身的质量，决定了你对产品质量的认知。** 裁判不准，你连自己做得好不好都不知道。

## 七、评测流程

```
1. 准备评测集（505 条用例）
        ↓
2. 批量运行系统，收集 actual_response
        ↓
3. 确定性预检（代码级）
   ├─ must_not 检测
   └─ expected_points 匹配
        ↓
4. LLM 裁判打分（7 维度）
        ↓
5. 预检覆盖修正
   （代码结果覆盖 LLM 可能的误判）
        ↓
6. 统计分析
   ├─ 整体通过率/各维度得分
   ├─ 各分支通过率
   └─ 失败用例根因分类
        ↓
7. 输出评测报告
   ├─ 数据看板
   ├─ 失败用例清单
   └─ 优化建议
```

## 八、根因分析方法

### 失败用例分类法

每次评测后，对失败用例按根因分类：

| 根因类别 | 说明 | 对应优化方向 |
|----------|------|-------------|
| 路由错误 | 走错了分支 | P2 修复 |
| 检索未命中 | 知识库没召回相关内容 | 知识库扩充 / 检索调优 |
| 信息不全 | 检索到了但没答全 | P3 优化（LLM 生成约束） |
| 幻觉 | 编造了知识库没有的内容 | 防幻觉机制 / prompt 约束 |
| 用例问题 | 用例期望设置有误 | 修正用例 |
| 裁判误判 | 裁判打错了分 | 升级裁判 |

### 杠杆维度识别

计算各维度得分与整体通过率的相关性，找到"杠杆维度"——改善它对整体提升最大。

> 这是一个高效迭代的策略：不要平均用力，优先优化影响最大的那个维度。
