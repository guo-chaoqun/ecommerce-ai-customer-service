这不是一个"调了调 API"的玩具项目，而是一套完整的**AI 产品方法论实践**：

| 阶段 | 内容 | 核心产出 |
|------|------|---------|
| **Phase 1 · 市场洞察** | 淘宝/京东/拼多多智能客服竞品分析 | 竞品评测维度 + SWOT + 差异化定位 |

| **Phase 3 · 质量体系** | 多维度评测与根因分析 | 505 用例评测体系 + 复评方法论 + 双通道判分 |

**核心数据成果：** 通过率 91.5% → 97.0% · 幻觉率 8.3% → 2.6% · 违规率归零

## 🎯 为什么做这个项目

很多人做 AI 客服项目，上来就"接个大模型 + 挂个知识库"就完事了。但我想搞清楚三个问题：

1. **市场上的 AI 客服到底做到什么水平了？** → 做了竞品分析
2. **如果我来做，应该怎么差异化？** → 推导了定位并搭了系统
3. **怎么证明我做的东西真的好用？** → 建了评测体系

> 一句话总结：我不是在"做一个客服机器人"，而是在**练习用产品方法论做 AI 产品**。

## 🚀 Phase 1 · 竞品分析

**研究对象：** 淘宝店小蜜、京东京小智、拼多多客服 + 智齿/晓多等 SaaS 产品

**竞品评测维度（5 项）：**
- 功能覆盖 · 对话体验 · 导购转化 · 售后办理 · 数据分析运营

**核心发现：**
- 头部玩家已从"降本工具"升级到"增长引擎"（京小智 5.0 内测转化率 +37%）
- 平台原生产品有天然边界——店小蜜不可能服务京东商家
- 多平台商家需要统一客服工具，但市场上缺乏好方案

**差异化定位：** 面向**多平台中小商家**的**可定制全渠道 AI 客服**
- 🌐 全渠道统一：一套知识库管理全平台
- 💡 极致可定制：可视化工作流拖拽搭建
- 🔒 数据自主权：支持私有化部署

## ⚙️ Phase 2 · 系统搭建

### 技术选型：为什么选 Dify Chatflow？

| 选项 | 优势 | 劣势 | 为什么不选 |
|------|------|------|-----------|
| 自研（LangChain） | 完全可控 | 重复造轮子，效率低 | 产品验证阶段不值得 |
| 闭平台（店小蜜） | 接入简单 | 封闭生态，不可定制 | 违背"全渠道"定位 |
| **Dify Chatflow** | 可视化 + 开源 + RAG 内置 | 高级能力需二开 | 完美匹配定位 |

### 三层漏斗架构

```
用户输入
    ↓
[第 1 层] 意图分类 LLM（温度 0.3）
    ├─ 知识类（疑问语气）→ 知识检索 → LLM 生成
    ├─ 办理类（祈使语气）→ 业务大类路由 → 分支处理
    ├─ 混合意图 → 核心诉求判定法 → 分流
    └─ 低置信度/闲聊 → 兜底/转人工
```

**8 个 IF/ELSE 分支：** 商品咨询 / 订单查询 / 退款换货 / 投诉 / 其他 / 多轮状态机 × 3

### V1→V2 迭代（10 项核心优化）

**P2 路由硬错误修复（7 项）：**
- 分类器咨询 vs 办理区分
- 换货场景细化
- 投诉类排除规则（"找人工"不=投诉）
- **混合意图核心诉求判定法**（重点！）
- 改单/取消纳入售后大类
- 其他类扩充（非电商场景）
- 新增取消/修改处理节点

**P3 信息完整性优化（3 项）：**
- LLM 润色 150→200 字 + 完整性约束
- 政策咨询关键词扩充
- 物流/服务不满场景补全

## 📊 Phase 3 · 评测体系（最有技术含量的部分）

### 评测集设计

- **505 条用例**，覆盖 8 大分支、5 种测试类型、3 个难度等级
- 每条用例 17 个字段，case_id 跨版本追踪

| 测试类型 | 说明 | 示例 |
|----------|------|------|
| 单轮功能 | 基础场景覆盖 | "发货时效是多久？" |
| 边界值 | 模糊/临界场景 | "物流太慢了"（投诉？咨询？） |
| 禁止表述 | 合规红线检测 | "加我微信"（应该拒答） |
| 多轮对话 | 上下文连贯性 | 退款流程多轮引导 |
| 对抗测试 | 恶意诱导/混合意图 | "退钱还要曝光你们" |

### 双通道判分机制

```
评测输入
    ├─ 确定性预检（代码级）
    │   ├─ must_not 精确匹配 → 违规判定
    │   └─ expected_points 宽松匹配 → 要点覆盖
    │
    └─ LLM 裁判 v4.4（语义级）
        └─ 7 维度 1-5 分打分
```

### 裁判系统迭代（v4.0 → v4.3 → v4.4）

**v4.3 核心突破：行为特征判定法**

> 旧裁判犯了一个低级错误——看到"退款"两个字就判退款分支。
>
> 但实际上，"退款多久到账"是**咨询政策**（商品咨询分支），"我要退款"才是**办理动作**（退款换货分支）。
>
> 区别不在于说什么（话题内容），而在于做什么（行为模式）。

| 分支 | 行为特征 | 典型表现 |
|------|----------|----------|
| 商品咨询 | 直接解答 | 给答案、不索要订单号 |
| 退款换货 | 引导办理 | 确认意向、要订单号 |
| 订单查询 | 查询数据 | 提供实时物流/状态 |
| 投诉 | 处理追责 | 道歉、记录、升级 |

### 复评方法论

**问题：** 直接对比 V2 和 V3 的评测结果不公平——因为两个版本用了不同的裁判和用例定义。

**解法：** 用同一套 v4.4 裁判 + 修正用例，对 V2 的原始回复重新打分。

**反直觉发现：** 旧裁判系统性低估了风险——V2 幻觉率旧口径 3.0%，复评后 8.3%。

### 最终成果

| 指标 | v1（基线） | V3 | 提升 |
|------|-----------|-----|------|
| 通过率 | 91.5% | 97.0% | +5.5pp |
| 幻觉率 | 8.3% | 2.6% | -5.7pp |
| 违规率 | 8.9% | 0% | -8.9pp |

## 💡 关键方法论沉淀

这个项目我觉得最有价值的不是"做了一个客服机器人"，而是沉淀了几个可迁移的方法论：

1. **复评口径** — 版本对比的公平性保障
2. **双通道判分** — 确定性 + 语义的平衡设计
3. **行为特征判定法** — 从"看内容"到"看行为"的认知升级
4. **P2/P3 分层优化** — 先修正确性，再提完整性的优先级判断
5. **三层漏斗架构** — 可解释、可调试、可优化的 RAG 系统范式
